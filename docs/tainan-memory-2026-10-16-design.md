## 3. 實測時刻怎麼重建（`.cache/tainan-1016-analysis/recon.py`，移進 repo 改名 `scripts/tainan_actuals.py`）

1. 每個有實測的站給兩個錨點：
   - 到站（或通過）：歷史資料取第一筆 SrcUpdateTime；D1 取 obs_at 減 32 秒。
   - 離站：表定離站＋max(0, 60×延誤分鐘數 − 30 秒)，且不早於到站後 20 秒。
2. 用加權保序回歸修掉前後矛盾。設下限：停站至少 20 秒，站間行駛時間至少是表定的 0.7 倍。
3. 沒有實測的站：停站時間照表定，只伸縮站間行駛時間。多出來的時間算成「留置」，放在最近一個沒有實測的停靠站。
4. 準確度：用 9/12 的秒級歷史資料回測，停靠站誤差中位 26 秒，p90 79 秒。D1 的到站誤差約 ±30 秒，離站 p95 約 ±60 秒。
5. 重建好的時刻餵進既有的 `computeProfiles` → `motion`，加減速剖面全部重算。另外加一道物理可行性檢查：各車種在窗內的最高時速不得超過該車種上限，超過的就退回表定並列出。

## 4. 22:00 之後的單線雙向

- 官方說法：22:00 先封鎖東正線，23:00 全面封鎖。實測上 3782 在 23:17 才離開永康，比全面封鎖晚了約 17 分鐘。
- 實測顯示，22:14 起永康—保安之間的對向列車嚴格輪流進入同一條單線：145 在永康等 3278，3782 在保安等 145。
- 22:07–22:13 臺南—保安之間有兩組對向列車時間重疊（3277 南下分別對上 3778、3278 北上）。資料分不出原因，可能是封鎖到 22:14 才真正生效，也可能是那一段有沒觀測到的待避線。
- 建議做法（決定 B-1）：22:14 起進入永康—保安的南下列車改走西正線（也就是平常的北上股道）反向行駛；22:00–22:14 那 3 班照一般股道，畫面標「股道待確認」並寫明原因。
  - 前提是東正線對應的是南下那組股道。股道資料裡沒有東西正線的屬性，只是南下那組 way 位在東側約 5–25 公尺，這一點是推定。
  - 技術上要自建北上 way 的反向 walk，並逐班覆寫 `dispatch.plans[].pathIds`。
  - 渡線位置不明。如果需要在畫面範圍內渡線，那一段標「待確認」，不捏造渡線。
- 套用之後跑一次占用檢查：22:14 之後同一條單線上不得有對向重疊；剩下解不掉的照 9/12 的不確定時段做法顯示。

snapshot.json 在 9/12 schema 之外新增的欄位（P 產生，U 讀）：

- `trains[].mark`：`'last-ground'`（3782）、`'last-south'`（145），其餘班次不設。
- `trains[].timing`：`'observed'`（至少有一個實測錨點）或 `'scheduled'`（整班沒有實測）。
- `trains[].stops[]` 加四個欄位：
  - `schedArrSec`、`schedDepSec`：表定時間。
  - `src`：`'obs'`、`'interp'` 或 `'sched'`。
  - `holdSec`：比表定多停的秒數；90 秒以上才算留置。
  - 原有的 `arrSec`、`depSec` 改成重建後的實際時間。
- `events[]`：`{id, t, text, kind, train?}`，`kind` 是 `'official'`、`'observed'` 或 `'inferred'`。這是時間軸的資料，觀測類的時刻由 build 從重建結果算出，不手打；次日 06:00 通車的 `t` 是 86400+21600。
- `singleLine`：`{fromSec, toSec, section:['永康','保安'], note}`。
- `uncertainty.json` 的 intervals 每筆加 `reason`：`'track-overlap'` 或 `'single-line-unresolved'`。
- `defaultSec`：79200（22:00）。
- `timingSource`：`{primary:'tdx-historical'|'d1', d1Rows, histRows, calibration}`。
